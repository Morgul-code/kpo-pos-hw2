# ПОС — Преподавательская Оценка Студентов

Консольное приложение для учёта преподавательских оценок студентов. Разработано в рамках домашнего задания № 2 по дисциплине «Конструирование программного обеспечения».

Проект демонстрирует предметно-ориентированное проектирование (**DDD**), архитектуру **Ports and Adapters**, порождающий, структурный и поведенческий паттерны, внедрение зависимостей через **Google Guice**, автоматические тесты и экспорт результатов в CSV.

## Возможности

- Добавление и просмотр студентов.
- Создание и просмотр рубрикаторов оценивания.
- Добавление и просмотр критериев с названием, максимальным баллом и весом.
- Выставление, просмотр, исправление и отмена оценок конкретного студента по выбранному рубрикатору.
- Расчёт итоговой оценки с учётом весов критериев.
- Экспорт оценок и итогового результата в CSV-файл.
- Проверка ограничений предметной области и обработка ошибочного консольного ввода.

## Технологии

- **Java 25** — язык реализации.
- **Gradle** (wrapper включён в репозиторий) — сборка и запуск.
- **Google Guice 7.0.0** — DI-контейнер.
- **JUnit Jupiter 6.0.1** — автоматическое тестирование.
- **In-memory repositories** — хранение данных во время работы приложения.

Внешняя база данных не требуется.

## Запуск

Нужен JDK 25 либо настроенная возможность Gradle получить соответствующий Java toolchain.

Из корня репозитория:

```bash
# Запуск приложения
./gradlew :app:run

# Запуск тестов
./gradlew :app:test

# Проверка сборки
./gradlew :app:build
```

На Windows используется `gradlew.bat` вместо `./gradlew`.

### Основные команды меню

| Команда | Действие |
|---|---|
| 1 | Добавить студента |
| 2 | Показать студентов |
| 3 | Создать рубрикатор |
| 4 | Показать рубрикаторы |
| 5 | Добавить критерий |
| 6 | Показать критерии |
| 7 | Выставить оценку |
| 8 | Рассчитать итог |
| 9 | Показать оценки студента |
| 10 | Экспортировать результат в CSV |
| 11 | Исправить оценку |
| 12 | Отменить оценку |
| 0 | Выход |

Студент, рубрикатор и критерий выбираются по порядковому номеру из отображаемого списка (нумерация с 1).

### Пример работы

1. Создать студента «Иван Иванов».
2. Создать рубрикатор.
3. Добавить «Экзамен»: максимум **10**, вес **0.60**.
4. Добавить «Проект»: максимум **20**, вес **0.40**.
5. Выставить студенту **8** баллов за экзамен и **18** за проект.
6. Рассчитать итог — **84%**.
7. Выбрать пункт **10**, указать студента, рубрикатор и путь к CSV-файлу.

Чтобы проверить исправление и отмену: выберите пункт **11**, измените оценку за экзамен с 8 на 3 и убедитесь, что итог станет **54%**. Затем верните 8 (итог снова **84%**), отмените оценку за экзамен через пункт **12** и проверьте итог **36%**. Экспорт после отмены оставит поле `score` для экзамена пустым.

Формула основной (взвешенной) стратегии:

$$
\text{Итог} = \sum_{i=1}^{n} \frac{\text{балл}_i}{\text{максимум}_i} \cdot \text{вес}_i
$$

Для приведённого примера: `8 / 10 × 0.60 + 18 / 20 × 0.40 = 0.84`, то есть **84%**.

Если оценка по критерию отсутствует, её вклад в итог равен нулю. Отсутствующая оценка и выставленный нулевой балл различаются при просмотре экспортированных данных.

## Предметная область и DDD

### Единый язык предметной области (Ubiquitous Language)

- **Student (студент)** — человек, которого оценивают.
- **Rubric (рубрикатор)** — набор критериев и их весов.
- **Criterion (критерий)** — оцениваемая работа с максимальным баллом и весом.
- **Evaluation (оценка)** — факт выставления балла конкретному студенту за конкретный критерий заданного рубрикатора.
- **Score (балл)** — значение выставленной оценки.
- **Final score (итог)** — вычисляемый результат, а не независимо сохраняемое число.

### Сущности, Value Object и агрегаты

| Тип | Классы | Обоснование |
|---|---|---|
| Entity | `Student` | Имеет идентификатор `UUID` и ФИО. |
| Entity | `Criterion` | Имеет идентификатор, название, максимум и вес. |
| Entity / корень агрегата | `Rubric` | Управляет набором критериев и ограничивает суммарный вес. |
| Entity | `Evaluation` | Имеет собственный `UUID`; связывает студента, рубрикатор, критерий и балл. |
| Value Object | `Score` | Java `record`; определяется значением и не имеет собственной идентичности. |

`Rubric` рассматривается как корень агрегата для состава критериев. Оценки хранятся отдельно через `EvaluationRepository` и ссылаются на связанные объекты по их идентификаторам.

### Доменные правила (инварианты)

- ФИО студента и название критерия не могут быть пустыми.
- Максимальный балл критерия должен быть больше нуля; его вес — в диапазоне `(0, 1]`.
- Сумма весов критериев рубрикатора не может превышать `1`.
- Выставление оценки разрешено только после доведения суммы весов до `1`.
- Балл должен быть в диапазоне от `0` до максимума соответствующего критерия.
- Критерий должен существовать в выбранном рубрикаторе.
- Для пары студент–рубрикатор–критерий может существовать не более одной актуальной оценки: `EvaluationRepository` использует составной ключ и отклоняет дубликаты.
- Выставленную оценку можно исправить с сохранением `Evaluation.id` или отменить; исправление повторно проверяет диапазон баллов и не меняет ранее сохранённую оценку при ошибке.
- Обновить или отменить отсутствующую оценку нельзя; после отмены допускается новая оценка по этому же критерию.
- `InMemoryRubricRepository` запрещает заменять сохранённый рубрикатор другим объектом с тем же идентификатором.
- Через `PosFacade` нельзя добавлять критерии в рубрикатор после начала оценивания по нему.
- Расчёт итога проверяет полноту весов, принадлежность оценок студенту и рубрикатору, существование критериев и отсутствие дубликатов.

Проверки распределены по соответствующим объектам и сервисам: `Criterion`, `Rubric`, `Score`, `Evaluation`, `EvaluationFactory`, `EvaluationApplicationService`, `FinalScoreService` и `PosFacade`. Часть правил, затрагивающих несколько сущностей или хранилище, обеспечивается на уровне сценария использования.

Итог не хранится как отдельная сущность: он вычисляется `FinalScoreService` на основании текущего рубрикатора и списка оценок.

## Архитектура — Ports and Adapters

Выбрана облегчённая реализация **Ports and Adapters (Hexagonal Architecture)** с разделением на доменный, прикладной, инфраструктурный и интерфейсный уровни.

```text
app/src/main/java/ru/kokoev/pos/
├── App.java                          # Точка входа, создание Guice Injector
├── domain/
│   ├── model/                       # Student, Rubric, Criterion, Evaluation, Score
│   ├── repository/                  # Порты репозиториев
│   ├── service/                     # FinalScoreService
│   ├── factory/                     # EvaluationFactory
│   └── strategy/                    # ScoringStrategy и реализации
├── application/
│   ├── facade/                      # PosFacade
│   ├── service/                     # EvaluationApplicationService
│   └── port/                        # ResultExporter
├── infrastructure/
│   ├── persistence/                 # In-memory реализации репозиториев
│   ├── export/                      # CsvResultExporter
│   └── di/                          # PosModule (конфигурация Guice)
└── presentation/
    └── console/                     # ConsoleMenu
```

Направление взаимодействия при выставлении оценки:

```text
ConsoleMenu
    → PosFacade
        → EvaluationApplicationService
            → EvaluationRepository (порт)
            → EvaluationFactory → Evaluation / Score (Domain)

InMemoryEvaluationRepository ── реализует ──> EvaluationRepository
```

Направление взаимодействия при экспорте:

```text
ConsoleMenu → PosFacade → ResultExporter (порт)
                                    ↑
                     CsvResultExporter (адаптер)
```

**Зависимости направлены к абстракциям и предметной логике.** Домен не импортирует Guice, консольные классы или классы файлового ввода-вывода. Инфраструктура реализует заданные портами контракты, а сборка объектов находится на внешней границе приложения.

## Паттерны проектирования

### 1. Фабрика — порождающий подход

**Класс:** `domain.factory.EvaluationFactory`.

**Проблема:** создание `Evaluation` требует формирования идентификатора, `Score`, проверки полноты рубрикатора и соблюдения доменных инвариантов. При исправлении необходимо сохранить исходный идентификатор оценки.

**Решение:** фабрика предоставляет перегруженные методы `create(...)`: с генерацией нового UUID для первой оценки и с заданным UUID для исправления. `EvaluationApplicationService` не конструирует оценку самостоятельно, а вызывает фабрику и сохраняет только успешно созданный объект. Проверки, уже принадлежащие самой сущности `Evaluation`, не дублируются.

Это простая фабрика (**Simple Factory**), применённая в качестве предлагаемого в задании порождающего решения; она не выдаётся за классический GoF Factory Method с переопределением фабричного метода в подклассах.

### 2. Facade — структурный GoF

**Класс:** `application.facade.PosFacade`.

**Проблема:** консольному интерфейсу пришлось бы напрямую управлять репозиториями, доменными объектами, расчётом и экспортом.

**Решение:** фасад предоставляет согласованные операции `createStudent`, `createRubric`, `addCriterion`, `assignScore`, `updateScore`, `removeScore`, `findEvaluations`, `calculateFinal`, `exportResult`. Консоль не зависит от деталей прикладных сервисов и хранения.

### 3. Strategy — поведенческий GoF

**Интерфейс:** `domain.strategy.ScoringStrategy`.

**Реализации:** `WeightedScoringStrategy`, `EqualWeightScoringStrategy`.

**Проблема:** способ вычисления итогового результата может меняться, но общая проверка корректности оценок должна оставаться неизменной.

**Решение:** `FinalScoreService` проверяет входные данные, затем делегирует математику внедрённой стратегии. По умолчанию в `PosModule` используется `WeightedScoringStrategy`. Для переключения на равновесный расчёт достаточно заменить привязку `ScoringStrategy` на `EqualWeightScoringStrategy` в DI-конфигурации.

- **Weighted:** сумма нормализованных баллов, умноженных на вес критериев.
- **Equal Weight:** среднее нормализованных баллов по *всем* критериям, в том числе ещё не оценённым (для них вклад равен нулю).

Для исходного примера Weighted даёт **84%**, Equal Weight — **85%**. Требование суммы весов `1` сохраняется для обеих стратегий.

## Dependency Injection

Контейнер **Google Guice** конфигурируется в `infrastructure.di.PosModule`.

- Интерфейсы `StudentRepository`, `RubricRepository`, `EvaluationRepository` связываются с in-memory реализациями.
- `ScoringStrategy` связывается с `WeightedScoringStrategy`.
- `ResultExporter` связывается с `CsvResultExporter`.
- Сервисы, фасад и консольное меню предоставляются через `@Provides`.
- Репозитории зарегистрированы как `Singleton`, чтобы все операции одного запуска использовали общие данные.

В `App.main()` создаётся `Injector`, из которого запрашивается `ConsoleMenu`. В доменную модель аннотации или зависимости Guice не добавляются.

## Экспорт CSV

Экспорт реализован через порт `application.port.ResultExporter` и адаптер `infrastructure.export.CsvResultExporter`.

Столбцы выходного CSV:

```csv
student_id,student_name,rubric_id,criterion_name,score,max_score,weight,final_percent
```

Для каждого критерия создаётся отдельная строка. Текстовые поля экранируются по правилам CSV: заключаются в двойные кавычки, внутренние двойные кавычки удваиваются. Кодировка — **UTF-8**. Если оценки нет, поле `score` остаётся пустым; если выставлено `0`, записывается `0`.

Итог рассчитывается в доменном сервисе **до** вызова экспортёра. Если расчёт неуспешен, запись файла не начинается. Ошибки файлового ввода-вывода отображаются в консоли без аварийного завершения основного меню.

**Важно:** при успешном экспорте существующий файл по выбранному пути перезаписывается. Родительская директория должна существовать. Чтобы однозначно выбрать расположение файла, можно указать абсолютный путь.

## Тестирование

Тесты расположены в `app/src/test/java/ru/kokoev/pos/` и используют JUnit Jupiter.

Проверяются:

- корректность создания сущностей и Value Object;
- диапазоны баллов, веса, принадлежность критерия и запрет дублирования оценок;
- взвешенный и равновесный расчёты, округление и отсутствующие оценки;
- операции репозиториев и прикладных сервисов, включая исправление и удаление оценок, сохранение идентификатора при исправлении, запрет дубликатов по составному ключу и невозможность подмены рубрикатора по UUID;
- сквозные сценарии консольного меню;
- конфигурация Guice, общие Singleton-репозитории и изоляция между контейнерами;
- формирование CSV, экранирование, отсутствие оценок и ошибки записи;
- отсутствие создания или перезаписи файла при ошибке доменного расчёта.

Для файловых тестов используется `@TempDir` — временные каталоги JUnit.

Запуск всех тестов: `./gradlew :app:test`.

## Ограничения текущей версии

- **Хранение только в оперативной памяти:** после завершения программы студенты, рубрикаторы и оценки не сохраняются. CSV экспортируется на диск отдельно.
- **Оценки можно исправлять и отменять через консоль:** команды 11 и 12. Повторное создание оценки без предварительной отмены запрещено. Отмена удаляет текущую оценку; отдельная история изменений не ведётся.
- **Один режим оценки на запуск:** алгоритм выбирается через конфигурацию Guice, а не пункт меню.
- **Запрет изменения рубрикатора после начала оценивания обеспечивается фасадом:** прямое изменение объекта `Rubric` из внешнего Java-кода в обход фасада не блокируется. Консольный интерфейс использует фасад.
- **CSV перезаписывается при экспорте:** подтверждение перезаписи не предусмотрено.
